### 新增护栏：确定性卡死 run 的"投毒"机制
种子固定（`22260912+1000×题号+run`）⇒ **卡死的 run 重驱必定再卡**，旧 driver 会在一个槽位上
反复烧满 `SLICE_TIMEOUT`（8 轮 × 4 h），扫描永不收敛。做法：driver 记每个切片的退出码
（`logs/<KEY>/rc_part<NN>.txt`，`<runs>|<rc>`）；`timeout` 杀进程返回 **124**；
同一片同一 run 列表被 124 杀 **≥2 次** → `mark_poison.py` 把**列表里第一个磁盘上没有 .mat 的 run**
写进 `logs/<KEY>/poison.txt`（切片按序执行且完成的 run 都原子落盘，所以第一个缺的就是卡死的那个，
它后面的只是没轮到）；`missing_runs.py` 据 `FE500_POISON` 跳过这些对；driver 收尾记 `poisoned=<n>`；
**验收脚本会把这些缺口报成 MISSING，不会被悄悄吞掉**。要求 2 次是为了不把"只是慢"误判成卡死。

## 00:05–00:15 用户反馈"CPU 利用率还是很低" → 定位并修掉启动节流 + 加内存闸

**诊断**：采样 6 次只有 **2–3 个 MATLAB** 在跑（上限 14），CPU ≈12–15%。日志显示切片启动
被卡在**固定每 22 s 一片**（`sleep 20`），而一个 SSDE 切片只要 ~25 s ⇒ 池子永远填不满。
`sleep 20` 本是为防"多进程同时**冷启动**导致 ntdll 堆损坏"，但对切片比它短的算法就成了纯吞吐限制。

**修复 1 —— 冷/热分段节流**：`LAUNCH_GAP=20` 只用在每次 pass 的**前 `COLD_STARTS=4` 次**启动，
之后用 `LAUNCH_GAP_WARM=5`。危险的是冷启动，不是稳态。效果：间隔 22 s → ~8 s，
SSDE 两分钟内 149 → **256/320**。

**修复 2 —— 内存闸**：实测每 worker 0.6 GB（SSDE）~1.2 GB（patternnet/dacefit 类）；
本机 31.3 GB 但 OS+应用已吃 ~16 GB，**基线空闲仅 16.8 GB**。
14 路跑 REMO/PACDIS/HES 时可能换页，**换页代价远大于多两个槽位**。
所以每次启动前查 `MIN_FREE_MB=3500`，不够就 `wait -n` 等一个切片结束
⇒ **池子自动按内存缩容，够时保持 14**，不用手调 MAXJOBS。

**定时巡检**（用户要求）：自动化 `852747ad-1eec-4afc-a421-6ca505c29ed6`，**每小时**，
有效到 **09-21 20:00**。prompt 写全了数据/日志路径、满额 2240、进程数与空闲内存、当前算法、
ETA、异常排查（`poison.txt` / `rc_part*.txt` 的 124 / `*.tmp.mat`），并且
"进程数为 0 且进度 < 2240 ⇒ driver 死了，报警但**不要自己重启**"。
