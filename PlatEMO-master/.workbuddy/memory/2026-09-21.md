### 🔴 新增护栏：确定性卡死 run 的"投毒"机制
**问题**：种子是 `22260912+1000×题号+run` 固定的 ⇒ **卡死的 run 重驱必定再卡**。
旧 driver 每轮都会重驱同一批缺口，一个卡死 run 会在一个槽位上反复烧满 `SLICE_TIMEOUT`
（8 轮 × 4 h），整个扫描永远收敛不了。

**做法**（新增 `mark_poison.py`，`missing_runs.py` 与 `driver.sh` 配套改动）：
1. driver 给每个切片记录退出码日志 `logs/<KEY>/rc_part<NN>.txt`，行格式 `<runs>|<rc>`；
2. `timeout` 杀进程返回 **124**；同一片**同一个 run 列表**被 124 杀掉 **≥ `MAX_SLICE_FAILS`（默认 2）次**
   → 调 `mark_poison.py`；
3. `mark_poison.py` 的判据很干净：切片按顺序执行且每个完成的 run 都原子落盘，
   所以**列表里第一个磁盘上没有对应 .mat 的 run 就是卡死的那个**（它后面的 run 只是没轮到）。
   只把这一个 run 写进 `logs/<KEY>/poison.txt`（`<part>|<run>`），其余尾部照常重驱；
4. `missing_runs.py` 读 `FE500_POISON` 跳过这些对；driver 启动时会把已有的 poison 列表打出来，
   收尾时把 `poisoned=<n>` 记进日志。**验收脚本会把这些缺口报成 MISSING，不会被悄悄吞掉。**

要求"2 次"是为了防止把**只是慢**的 run 误判成卡死。

### 🔍 顺带查清：**DTLZ7 单跑 wall 被指标计算主导（~100 s/跑）**
重启后观察到"只有 1 个 MATLAB 在跑"，一度以为节流又坏了。实际原因不是节流，而是
**SSDE 只剩一片 7 跑的 DTLZ7 切片**，而 DTLZ7 的单跑 wall 是 **86–130 s**，同时
**`metric.runtime` 只有 1.2–1.6 s** —— 也就是说算法本身 1.5 s，剩下 ~100 s 全是指标计算。

机理：DTLZ7 的 `GetOptimum` 用 `UniformPoint(N, M-1, 'grid')`，**M=20 时给出
2¹⁹ = 524288 个参考点**（其它题是 `UniformPoint(10000, M-1)` 的 10000 点）。
于是每个快照的 IGD/IGDp 要算 `524288 × |存档|` 的距离，30 快照 × 2 指标 ≈ 100 s。
对照：同算法 DTLZ1/DTLZ2/WFG9 的单跑 wall 只有 2.5–5 s。
⇒ 这是"要 IGDp 全轨迹"的必然代价（旧笔记那句"DTLZ7/M=20 参考集 524288 点、进池会崩"
就是同一件事）。对 REMO/PACDIS/HES（单跑几百秒）可忽略；对 SSDE 这种秒级算法会明显拖尾
（20 跑 ≈ 33 min）。**看单跑成本必须看日志里的 `wall`，不能看 `metric.runtime`。**

⇒ 顺带结论：某一时刻 MATLAB 进程数少，**先分清是"节流/池子问题"还是"只剩一个长切片在串行"**，
两者的处置完全不同。这次的病根是后者（重启后遗留的碎片缺口），不需要再改 driver。

### 加了 `split_starved()`：活儿不够分时自动细分切片（`missing_runs.py`）
- 规则：算完自然切片后，若 **片数 < `FE500_MAXJOBS`（默认 16）**，就把**最大的片对半切**，
  直到片数达标或**任何片都切不动**（两半都 ≥ `FE500_MINCHUNK`，默认 3）。
- **为什么有 MINCHUNK**：本机 2 跑/切片那种超短切片正是 `-batch` 崩溃高发的配置
  （旧账：2 跑/切片 20 片崩 6 片 vs 10 跑/切片 156 片全 exit=0），所以 3 是地板不是建议。
- **为什么必须现在做**：`missing_runs.py` 是**每一轮 attempt 现调**的，
  所以改完**不用重启 driver**，下一次 attempt 就生效 —— 零停机。

### 记住的读数方法
本机可用 **`/proc/stat` 的 `cpu` 行做两次差分**算真实 CPU 利用率（MSYS 里有）：
`user+nice+system+idle+iowait+irq+softirq+steal` 求总和、`idle` 单列，两次采样求 `(dt-di)/dt`。
比数进程数靠谱（进程数会被波尾误导）。

### DTLZ7 的 IGDp 成本随存档规模放大（01:59 实测，影响 ETA）

之前 SSDE 只多 ~100 s 是因为它存档只有 100 点。⇒ **REMO/PACDIS/HES 的存档更大，DTLZ7 会拖更多**，
估计每个算法 DTLZ7 这一题会让整轮 wall 多 ~40–60 min（它是 32 片里的"长杆"）。
这是"每题每个快照都要 IGDp"的固有代价，与既有 20目标 数据同口径，不能降（降了就不可比）。
