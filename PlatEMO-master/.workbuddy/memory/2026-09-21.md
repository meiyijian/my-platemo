### 🔴 新增护栏：确定性卡死 run 的"投毒"机制
**问题**：种子是 `22260912+1000×题号+run` 固定的 ⇒ **卡死的 run 重驱必定再卡**。
旧 driver 每轮都会重驱同一批缺口，一个卡死 run 会在一个槽位上反复烧满 `SLICE_TIMEOUT`
（8 轮 × 4 h），整个扫描永远收敛不了。

**做法**（新增 `mark_poison.py`，`missing_runs.py` 与 `driver.sh` 配套改动）：
1. driver 给每个切片记录退出码日志 `logs/<KEY>/rc_part<NN>.txt`，行格式 `<runs>|<rc>`；
2. `timeout` 杀进程返回 **124**；同一片**同一个 run 列表**被 124 杀掉 **≥ `MAX_SLICE_FAILS`（默认 2）次**
   → 调 `mark_poison.py`；
3. `mark_poison.py` 的判据很干净：切片按顺序执行且每个完成的 run 都原子落盘，
   所以**列表里第一个磁盘上没有对应 .mat 的 run 就是卡死的那个**（它后面的 run 只是没轮到）。
   只把这一个 run 写进 `logs/<KEY>/poison.txt`（`<part>|<run>`），其余尾部照常重驱；
4. `missing_runs.py` 读 `FE500_POISON` 跳过这些对；driver 启动时会把已有的 poison 列表打出来，
   收尾时把 `poisoned=<n>` 记进日志。**验收脚本会把这些缺口报成 MISSING，不会被悄悄吞掉。**

要求"2 次"是为了防止把**只是慢**的 run 误判成卡死。

## 00:05–00:15 用户反馈"CPU 利用率还是很低" → 定位并修掉**启动节流**（第三次重启）

### 诊断（实测，不是猜）
采样 6 次：**只有 2–3 个 MATLAB 在跑**（上限 14），CPU ≈ 12–15%。日志显示切片启动被卡在
**固定每 22 s 一片**（`sleep 20` + 开销），而**一个 SSDE 切片只要 ~25 s** ⇒ 前一片刚跑完、
下一片还没启动，进程池永远填不满。
根因：`sleep 20` 是为"本机多进程同时**冷启动**会 ntdll 堆损坏"设的保守间隔，
但它对**切片时长 < 间隔**的算法（SSDE）变成了纯粹的吞吐限制器。

### 修复 1：冷/热分段节流
`LAUNCH_GAP=20`（每次 pass 的**前 `COLD_STARTS=4` 次**启动用，保护冷启动）、
`LAUNCH_GAP_WARM=5`（之后用）。危险的是**冷启动**，不是稳态。
效果：启动间隔 22 s → ~8 s，SSDE 两分钟内 149 → **256/320**，进程数 2–3 → 14。

### 修复 2：内存闸（比降 MAXJOBS 更好）
实测每 worker 占 0.6 GB（SSDE）~1.2 GB（patternnet/dacefit 类）；
本机 31.3 GB 总内存但 OS+应用已吃 ~16 GB，**基线空闲只有 16.8 GB**。
14 路跑到 REMO/PACDIS/HES 时可能开始换页——**换页风暴的代价远大于多两个槽位的收益**。
所以每次启动前检查 `MIN_FREE_MB=3500`，低于就 `wait -n` 等一个切片结束再启。
⇒ **池子会自己按内存缩容，内存够时保持 14**，不需要用户手调 MAXJOBS。

### 🔍 顺带查清：**DTLZ7 单跑 wall 被指标计算主导（~100 s/跑）**
重启后观察到"只有 1 个 MATLAB 在跑"，一度以为节流又坏了。实际原因不是节流，而是
**SSDE 只剩一片 7 跑的 DTLZ7 切片**，而 DTLZ7 的单跑 wall 是 **86–130 s**，同时
**`metric.runtime` 只有 1.2–1.6 s** —— 也就是说算法本身 1.5 s，剩下 ~100 s 全是指标计算。

机理：DTLZ7 的 `GetOptimum` 用 `UniformPoint(N, M-1, 'grid')`，**M=20 时给出
2¹⁹ = 524288 个参考点**（其它题是 `UniformPoint(10000, M-1)` 的 10000 点）。
于是每个快照的 IGD/IGDp 要算 `524288 × |存档|` 的距离，30 快照 × 2 指标 ≈ 100 s。
对照：同算法 DTLZ1/DTLZ2/WFG9 的单跑 wall 只有 2.5–5 s。
⇒ 这是"要 IGDp 全轨迹"的必然代价（旧笔记那句"DTLZ7/M=20 参考集 524288 点、进池会崩"
就是同一件事）。对 REMO/PACDIS/HES（单跑几百秒）可忽略；对 SSDE 这种秒级算法会明显拖尾
（20 跑 ≈ 33 min）。**看单跑成本必须看日志里的 `wall`，不能看 `metric.runtime`。**

⇒ 顺带结论：某一时刻 MATLAB 进程数少，**先分清是"节流/池子问题"还是"只剩一个长切片在串行"**，
两者的处置完全不同。这次的病根是后者（重启后遗留的碎片缺口），不需要再改 driver。

## 00:35 🔴 重大 bug：`ALGS` 里把 `SAMOEATL2M` 当键名 —— **整轮 driver 被 `exit 2` 干掉**

### 现象
后台任务 `r45VsU` 11 分 37 秒就"完成"了（本该 16 h）。输出末尾：
```
[00:34:47] ---------- SSDE done: present=320/320  poisoned=0 ----------
unknown algorithm key 'SAMOEATL2M'
```
⇒ **SSDE 跑完了 320/320，但后面 6 个算法一个都没启动。**
（00:23 那次和更早的 00:00 那次都是同一个毛病，只是我都在它走到 SAMOEA 之前就手动停了，没暴露。）

### 根因（两层）
1. **键名 vs 类名不一致**：registry / python / driver 的 `case` 用的规范键是 **`SAMOEA`**，
   而**类名与输出目录名是 `SAMOEATL2M`**。我传给 `ALGS` 的是类名 → `case` 落到 `*)` 分支
   → `echo ... ; exit 2` → **整个 driver 退出**（不是跳过这一个算法）。
2. **更隐蔽的一层**：`missing_runs.py` / `mark_poison.py` 拼 MAT 文件名时用的是**键名**，
   但实际文件名用的是**类名**（harness 的 `o.Algorithm` = `R.cls`）。
   七个算法里只有 SAMOEA 两者不同 ⇒ 用 `FE500_ALG=SAMOEA` 时这两个脚本会去找
   `SAMOEA_*.mat`，**一个都找不到 ⇒ 认为 320 个全缺**（然后每片被 harness 按类名文件名跳过，
   白排 32 片空转）。这个坑当时还没爆出来，是一起发现的。

### 修复（四处）
- `driver.sh`：`case` 接受 `SAMOEA|SAMOEATL2M`（别名）；命中别名时把 `key` 归一成 `SAMOEA`。
- `driver.sh`：**未知键不再 `exit 2`** —— 改成打印 `!! unknown algorithm key ... -> SKIPPED`、
  记进 `BADKEY`、`continue`；脚本末尾汇总 `!! UNKNOWN ALGORITHM KEY(S) SKIPPED: ...`。
  **教训：一个拼写错误不该有能力带走一整轮 16 h 的扫描。**
- `missing_runs.py`：新增 **`CLASSES` 表 + `resolve()`**，文件名一律用**类名**、
  目录用 `FOLDERS`（或 `FE500_FOLDER` 环境变量覆盖）；`SAMOEATL2M` 作为键别名同样接受。
- `mark_poison.py`：改用 `resolve()`（同样按类名拼文件名）。
- `run_FE500_M20.m`：`algKey='SAMOEATL2M'` 归一成 `'SAMOEA'`。
- `driver.sh`：导出 `FE500_FOLDER=$KEYDIR`，让"类覆盖 `FE500_CLS_<KEY>` 换目录"时
  python 侧也跟着走。
- 顺手修掉 `poison.txt` 不存在时 bash 打印 `No such file or directory` 的噪声。
