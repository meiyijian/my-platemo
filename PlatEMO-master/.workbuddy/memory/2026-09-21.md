### 🔴 新增护栏：确定性卡死 run 的"投毒"机制
**问题**：种子是 `22260912+1000×题号+run` 固定的 ⇒ **卡死的 run 重驱必定再卡**。
旧 driver 每轮都会重驱同一批缺口，一个卡死 run 会在一个槽位上反复烧满 `SLICE_TIMEOUT`
（8 轮 × 4 h），整个扫描永远收敛不了。

**做法**（新增 `mark_poison.py`，`missing_runs.py` 与 `driver.sh` 配套改动）：
1. driver 给每个切片记录退出码日志 `logs/<KEY>/rc_part<NN>.txt`，行格式 `<runs>|<rc>`；
2. `timeout` 杀进程返回 **124**；同一片**同一个 run 列表**被 124 杀掉 **≥ `MAX_SLICE_FAILS`（默认 2）次**
   → 调 `mark_poison.py`；
3. `mark_poison.py` 的判据很干净：切片按顺序执行且每个完成的 run 都原子落盘，
   所以**列表里第一个磁盘上没有对应 .mat 的 run 就是卡死的那个**（它后面的 run 只是没轮到）。
   只把这一个 run 写进 `logs/<KEY>/poison.txt`（`<part>|<run>`），其余尾部照常重驱；
4. `missing_runs.py` 读 `FE500_POISON` 跳过这些对；driver 启动时会把已有的 poison 列表打出来，
   收尾时把 `poisoned=<n>` 记进日志。**验收脚本会把这些缺口报成 MISSING，不会被悄悄吞掉。**

要求"2 次"是为了防止把**只是慢**的 run 误判成卡死。
